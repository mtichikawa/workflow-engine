A from-scratch AI workflow engine

Describe a task in plain English. Get an AI workflow you can check.

It builds the workflow out of small AI specialists, refuses to run a broken plan, stops for a person before anything leaves it, and learns a team's unwritten rules from their corrections. Every number below comes from a test set written separately from the engine, and can be re-run.

What the validator says about five of them

    How it works

    One sentence becomes a checked workflow of small, single-job specialists. A person approves before anything leaves it, and their corrections teach it.

    A shared library

    15 single-job specialists (classify, verify, match, extract, act…), one instance each. A workflow configures them; it never copies them. A new job mostly reuses what's on the shelf.

    Checked before it runs

    A static validator follows every wire and condition: each step must read something that exists and has already run, and any step that acts outside the engine must sit behind a human gate.

    Model where judgment is needed, code where it isn't

    Reading a scan or a message is a model call. Plan rules, the claim form and the safety sentence are plain code: the same every time, and auditable.

    Built with

    For a healthcare team

    Design facts, not compliance claims.

    Medical content goes to a person

    A written policy decides what counts as medical, including mental-health warning signs. The assistant never answers it; a nurse is alerted.

    Replies stay inside the line

    Patient replies cover coverage and scheduling only. The safety sentence is fixed text added by code, and a second model checks every draft before a person sees it.

    A record of every decision

    Nothing leaves without approval. The packet a person approves holds the claim, the reply, the nurse handoff, the open items, and every field with the document it came from.

    Model calls go to Anthropic's Claude; documents and results stay on the machine running the engine. It has not been tested on real patients or real payer systems.

    How it learns

    No fine-tuning. Each workflow keeps its own corrections, and nothing crosses between workflows or customers.

    1 · Instructions

    What the step is for: its categories, its criteria, any written policy. With no corrections, this is all it has.

    2 · A rulebook it writes

    From 8 corrections on, it reads all of them once and writes down the rules they imply, then rewrites them when a correction changes.

    3 · The closest examples

    On every call it also sees the 6 past corrections most like the current input, so the rules come with cases.

    The clinic's real rules (never shown to it)

      Rules it wrote from 291 corrections

        The first six of each, as written. Scored blind afterwards: 97.3% on 150 messages it never saw; with the real rules written out by hand: 100%. The honest comparison: pasting all 291 corrections into one long prompt scored — just as accurate. What the rulebook adds is a prompt about 40% the size, rules a person can read, diff and lock, and nothing that grows with every new correction.

        The workbench

        One page to make, keep, run and correct workflows: python -m engine.app. Describe a task, the composer drafts it, you adjust the steps in a form, and every save is a new version. Runs take pasted text, a CSV, a folder, a webhook, or a folder re-read on a schedule.

        How each number was measured

        1. A separate AI agent (Claude), with no access to the code or any training data, wrote the test set.
        2. A second, independent Claude agent labelled every item again; only items both agreed on were kept. No person checked the labels.
        3. The set was sealed with a hash before its first score, and scored once.
        4. A change to the engine means a new set, never a re-score.
        5. Every result carries its sample size, a baseline and a 95% confidence interval.

        Method and raw results: docs/blind-evals.md · evals/blind-results

        What it can't do yet

        • No real sending or submitting: no email, no claims portal, no eligibility check against a payer.
        • No general image reader: reading scans and photos exists only in the healthcare demo, and on a bad photo it leaves many fields for a person to fill (below).
        • One machine, no login: the workbench is for one computer or a private network.
        • Learning beats a long prompt on size, not accuracy, at a few hundred corrections.
        • Every test set and the engine itself use Claude models, so they may share blind spots. All test data is synthetic, and no person checked the labels.
        Bugs its own tests found (5)
        • A step reached by both a "pass" and a "fail" edge was always skipped, so the triage workflow's approval step never ran. Found by a seeded-fault test; fixed, with a regression test.
        • The validator crashed on an edge to a step that doesn't exist. Fixed.
        • The new validator caught the composer's own mistake: in the demo, its draft wired a list into a field that takes text. The composer now repairs it before running.
        • An approval step that came after the action. Driving the workbench in a browser showed a gated file step writing its file first and asking second; a rejected item had already written. Outside actions now wait for approval before they run.
        • Every item wrote the same file, and a saved workflow's corrections went into the shared example set. Staged files are never overwritten now, and each workflow learns in its own folder.

        More measurements

        Smaller or less independent than the four above, so they aren't headlines.
